## 1. 원칙

퀄리 UI 개발은 다음 절차를 따른다.

```text
요청 해석 → 기준 확인 → 설계 → 구현 → 검증 → 기록 → 해시 갱신 → 릴리즈 판단
```

모든 화면과 산출물은 다음 정보 흐름을 따른다.

```text
입력 → 기준 → 판정 → 근거 → 조치
```

---

## 2. 전체 절차도

```mermaid
flowchart TD
    A[요청 접수] --> B[요청 해석]
    B --> C[제품/모듈 고정]
    C --> D[헌법·가드레일 확인]
    D --> E[Memory 확인]
    E --> F[화면 목적 정의]
    F --> G[정보 구조 설계]
    G --> H[컴포넌트 선택]
    H --> I[구현]
    I --> J[접근성·토큰·상태·근거 검증]
    J --> K[문서 정합성·해시 검증]
    K --> L{재사용 결정 발생?}
    L -- 예 --> M[Memory 기록]
    L -- 아니오 --> N[릴리즈 판단]
    M --> N
    N --> O[PASS / HOLD / FAIL]
```

## 3. Step 1: 요청 해석

### 목적

사용자 요청을 작업 가능한 단위로 바꾼다.

### 필수 질문

- 무엇을 만들거나 바꾸는가?
- 대상 제품은 무엇인가?
- 대상 사용자는 누구인가?
- 사용자가 첫 10초 안에 해야 할 행동은 무엇인가?
- 적용 기준은 무엇인가?
- 산출물은 화면, 문서, 컴포넌트, 스킬, 보고서 중 무엇인가?

### 산출 템플릿

```text
요청:
목표:
대상 제품:
대상 사용자:
첫 행동:
입력:
기준:
판정 상태:
근거:
출력:
성공 조건:
HOLD:
```

## 5. Step 3: 설계

### 설계 순서

1. 화면 목적을 한 문장으로 정의한다.
2. 첫 행동을 한 문장으로 정의한다.
3. 입력 → 기준 → 판정 → 근거 → 조치 흐름을 작성한다.
4. 필요한 컴포넌트를 고른다.
5. 상태 값을 정의한다.
6. 모바일 순서를 정의한다.
7. 접근성 리스크를 예측한다.
8. Evidence Schema 필수 필드를 정의한다.
9. 검증 명령과 해시 갱신 필요 여부를 정의한다.

### 설계 산출물

```text
화면 목적:
첫 행동:
정보 흐름:
필수 컴포넌트:
상태 값:
모바일 순서:
접근성 리스크:
Evidence Schema:
검증 명령:
해시 갱신:
HOLD:
```

## 6. Step 4: 구현

### 구현 원칙

- 기존 토큰 우선
- 기존 컴포넌트 우선
- 새 스타일 최소화
- 의미 있는 HTML 구조
- 테이블에는 caption과 header 제공
- 버튼에는 type 명시
- 아이콘 버튼에는 aria-label 제공
- 상태에는 텍스트 라벨 제공
- focus-visible 유지
- Evidence 데이터는 `standard_id`, `revision`, `clause`, `source_file`, `evidence_level`, `verification_status`를 포함

### 금지

- 임의 HEX 하드코딩
- 임의 폰트 추가
- 인라인 스타일 남발
- 상태 색상 임의 추가
- evidence 없는 PASS
- 모바일에서 정보 순서 붕괴
- `REVIEWED`를 `READY` 또는 `PASS`처럼 표현
- 문서 변경 후 `SHA256SUMS.txt` 미갱신

## 7. Step 5: 검증

| 검증 항목 | 질문 | 판정 |
|---|---|---|
| 쉬움 | 초보자가 10초 안에 첫 행동을 알 수 있는가? | PASS/HOLD/FAIL |
| 표준성 | 표준번호·개정·기준이 보이는가? | PASS/HOLD/FAIL |
| 신뢰성 | 근거와 판정이 연결되는가? | PASS/HOLD/FAIL |
| 전문성 | 장식보다 구조와 근거가 앞서는가? | PASS/HOLD/FAIL |
| 간결성 | 한 화면 한 목적이 유지되는가? | PASS/HOLD/FAIL |
| 여백 | 정보 구분이 명확한가? | PASS/HOLD/FAIL |
| 접근성 | 대비, 포커스, 라벨이 충분한가? | PASS/HOLD/FAIL |
| 모듈성 | 다른 모듈과 같은 UI 문법을 쓰는가? | PASS/HOLD/FAIL |
| 근거 스키마 | Evidence 필수 필드가 충족되는가? | PASS/HOLD/FAIL |
| 문서 정합성 | 상태·토큰·컴포넌트 기준이 문서 간 일치하는가? | PASS/HOLD/FAIL |
| 해시 | 변경 후 `SHA256SUMS.txt`가 최신인가? | PASS/HOLD/FAIL |

## 9. Step 7: 해시 갱신

문서 또는 실행 기준 파일이 변경되면 릴리즈 판단 전 `SHA256SUMS.txt`를 갱신한다.

권장 순서:

```text
문서 수정 → 검증 실행 → SHA256SUMS 갱신 → 해시 검증 → 최종 보고
```

해시 검증이 실패하면 PASS로 보고하지 않는다.

---

## 10. Step 8: 릴리즈 판단

| 판정 | 의미 | 조건 |
|---|---|---|
| PASS | 사용 가능 | 기준 충족, 검증 완료, 해시 최신 |
| HOLD | 보류 | 확인 필요 항목 존재, 검증 일부 미완료 |
| FAIL | 차단 | 헌법·가드레일 위반 |

## 11. 제품별 워크플로우

```text
원본 입력 → 메타데이터 확인 → 표준번호 매핑 → 버전 상태 표시 → 원본 저장 → 검색 가능 상태
```

### 퀄리도서관

```text

```

### 브릿지

```text
고객 질문 → 기준 선택 → 답변 생성 → 근거 요약 → 다음 조치 → 보고/교육 연결
```

### 스킬업

```text
학습 목표 → 개념 설명 → 사례 → 실습 → 퀴즈 → 피드백 → 재학습
```
